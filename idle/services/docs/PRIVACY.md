# Service data inventory and deletion boundary

This describes implemented behavior. It is not a published legal policy, completed native SDK disclosure, or evidence of a hosted service.

| Data | Purpose | Collection and retention |
|---|---|---|
| Random account UUID, hashed recovery code and hashed session tokens | Optional account authentication | Only after cloud opt-in. Recovery code and token plaintext are returned once and never logged or stored by the service. Session lifetime 30 days, up to eight devices. |
| Full checksummed gameplay snapshots and branch metadata | Explicit cloud recovery | Uploaded only by the caller. Up to 64 MiB/10,000 snapshots; no silent branch deletion. Can include optional game settings, story state, and recovery references. No client credentials belong in a snapshot; sensitive key names are rejected. |
| Provider transaction identity, verified product/state/version/authority, acknowledgement | Restore and revoke cosmetic ownership | Stored separately from gameplay. Raw receipt proofs, advertising IDs and payment/card data are not retained by this service. A configured Google adapter retains purchase tokens only in the encrypted vault described below. The default local runner has no real provider configuration. |
| Encrypted Google purchase token, account UUID, opaque transaction ID, key ID, nonce and vault key commitments | Fresh provider reconciliation, refund and acknowledgement recovery | AES-256-GCM ciphertext is account/transaction/key-bound; encryption keys stay in a separate operator-controlled file. Plaintext tokens are excluded from exports and logs. Account deletion cascades through live token rows. Non-account key commitments remain to prevent accidental reuse of a key ID with different material. |
| Signed cosmetic lease, account/main-seed binding, revision and local time high-water state | Bounded offline presentation of verified ownership | Device secure storage, separate from saves. Maximum lease lifetime is 24 hours and also bounded by provider freshness. Logout clears grants but retains anti-replay high water; confirmed deletion erases the device record. Native opaque clock epochs stay on device. Apple process restarts require fresh online verification. |
| Daily Support source/receipt and delivered snapshot ID | Deduplicate the shared six slots | Current plus seven prior account days; explicit prune also removes expired rows from inactive accounts. No briefing content or ad-view profile is collected. |
| Defined session/progression/diagnostic events | Optional quality measurement | Separate consent required, at most 5,000/account and 90 days. Revocation deletes current events. No freeform text, wallet dump, receipt or email field. Client queue is bounded and memory-only. |
| Short-lived source-address SHA-256 hash, time bucket and count | Request abuse limits | Raw address is not stored in service tables. Hashes are pseudonymous, not anonymized; entries removed after two minutes. Proxy/server logs need a separate deployment audit. |
| Optional feature-switch audit | Operator accountability | Contains switch name, boolean and time, without account identity. |

Account export excludes credential hashes as well as raw credentials and proofs. Account deletion requires recovery confirmation and cascades through active service snapshots, claims, telemetry, sessions and purchase records. SQLite secure-delete is enabled and database/backup permissions are owner-only. These measures do not prove forensic erasure from filesystem snapshots, WAL copies, or remote backups. The production operator must provide a bounded backup-retention/erasure policy and apply deletion tombstones before restoring backups. No hosted backup exists in this task.

Deletion leaves the current local guest game intact. It does not cancel an Apple/Google store purchase. Future restoration after deletion must independently reverify store ownership and account binding; local paid flags are not retained as proof. No email, password or third-party login is required by the implemented recovery-code method. A lost code with no valid device session is not recoverable by inventing identity or copying another player's account.

Native collection must be reviewed separately: the existing purchase and advertising plugins can initialize network behavior outside this service. Until native consent/configuration checks and actual traffic inspection are complete, this inventory cannot be asserted to describe the complete application. Consent refusal and service outage must leave guest economy, local export and free briefing playable.

Analytics is off by default. After explicit account-bound consent, the actual app lifecycle records defined session/progression/diagnostic events and attempts bounded uploads. It records no pre-consent history. `ConsentTelemetryBuffer.optOut()` clears local events immediately. If the remote service cannot be reached, its `pendingRemoteOptOut` remains true and the error is reported. The native host must persist/surface that pending request and retry after reconnection; an unsuccessful request must not be displayed as completed remote deletion.

The native soundtrack export writes only the verified public audio archive into the application cache and passes it to a player-selected native destination. Bearer credentials remain in request headers and are never written into that archive. A completed personal export cannot be recalled by account deletion or a later refund. The destination app or storage provider is chosen by the player. The current export-cache policy reserves at most three recent exports of at most64MiB each, refuses another download at capacity, and removes files older than24hours on the next startup or export. Recent files are retained for receiving applications; the OS can evict cache files earlier. Legacy unrecognized/oversized entries fail closed rather than being deleted blindly. This bounded local policy has independent filesystem evidence; physical storage-pressure and receiving-app lifetime qualification remain open.

Current integration references: `game/mobile/lib/game_telemetry.dart`, `game/mobile/lib/native_services.dart`, `game/platform/OWNERSHIP_CLOCK.md`, and `services/docs/FULFILLMENT.md`. SDK traffic, deployment logs and retained-backup deletion still require separate actual-environment verification.

## Separate study collection under integration review

Normal builds omit `TIDEGLASS_STUDY_PROVISION`: no study registry is opened and no study history is recorded. A separately provisioned study build presents approved information/contact/retention wording and explicit opt-in before game bootstrap. The recorder stores random install/session/process IDs, consent/protocol/information hashes, a local eligibility-check hash, candidate/economy/content labels, coarse device/acquisition categories, timestamps and enumerated lifecycle/activity/gap events in app-private storage. After the current explicit consent, a separate native channel additionally records the app process PID, platform, app identifier/version/build and UTC observation time to support cautious linkage to separately supplied operating-system diagnostics. No device identifier, device uptime, crash handler, automatic log collection or diagnostic upload is added. Older consent text does not authorize the new fields; default, declined, legacy, exhausted and withdrawn states do not request them. An unavailable observation is recorded as a coverage gap, not invented context. It contains no account credentials, freeform player input, payment receipts or activity from before enrollment. The local empty-harbor check is supporting evidence; independent enrollment/eligibility review must establish a valid first-launch cohort.

The draft study settings route copies a verified raw/evidence bundle only after a separate clipboard warning and confirmation. A pasted copy may remain in another application. Default withdrawal stops collection and erases local identifiers/records and local eligibility evidence, leaving a nonidentifying stop marker; staff must handle previously exported copies under the actual approved retention/deletion policy. There is no study server/upload or live enrollment in this workspace. Host runtime/UI and synthetic diagnostic-linkage checks exist; current native execution, real diagnostic qualification and independent enrollment remain open. This paragraph is an engineering inventory, not consent approval or a completed study.
