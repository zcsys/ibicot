Initial QA015 source and both failures remain at `release/qa/integration-telemetry-initial-20261019T141159734022Z`. Its backend checks demonstrate that stale/withdrawn consent revisions are rejected; the client defect did not establish backend acceptance of unauthorized events. The corrected classification maps primarily to S39 consent behavior and secondarily to S27 privacy/support accuracy.

The independent suite also verifies that explicit withdrawal and account replacement invalidate in-flight reads; consenting while backgrounded creates no session until return; a late return response does not restart a background session; unknown delivery outcomes retry the same event IDs without altering gameplay; and a failed old-account delivery cannot clear the new account's observations. The actual-app author lifecycle test confirms that inactive does not end a session, paused does, return records a new session/resume result, and widget disposal does not fabricate a clean process exit. All are host tests, with injected service responses except the separately executed HTTP consent-read cases.

Source review confirms explicit consent, per-account/session binding, memory-only bounded buffering, event-ID retry, rejection of stale server revisions, and no gameplay writes by the observer. Consent reads are GET requests and never write a new opt-in. The eight independent test cases use real manager/observer/buffer logic. The queue does not survive process death, so an unfinished session is an unknown outcome. Observations can be dropped at queue capacity or retention expiry. No native crash signal is invented.

Measurement semantics remain limited. The observer reports current-session changes, not reconstructed pre-consent history. Multiple automatic Recharts or batched contract changes between notifications can produce one observed-change event; these events are not authoritative transaction counts. The build defaults to development and device class to unclassified unless configured. These constraints must be reflected in measurement documentation and aggregation before staging acceptance. Passing these tests does not establish a 10,000-session denominator, crash-free rate, retention rate, physical-device breakdown or any elapsed-user observation.

One initial regression invocation failed before tests loaded because concurrent Flutter jobs shared a native-asset output. That harness failure is retained separately; subsequent Flutter execution was serial. The final successful regression is independent of that failed invocation. No production code was edited by QA.

The two-direction scope audit preserves all 44 requirements and 65 original acceptance contracts/dependencies. M5-03/M5-04 and the broader package gates remain open. No package, staging gate, beta freeze, store release or physical-device qualification is accepted here.
