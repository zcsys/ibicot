# Exact uncovered M3-05 / S26 native reminder obligation

The original M3-05 says opt-in quiet-hour notifications “function across targets.” S26 requires the controls to work on named targets. Code is implemented; actual OS permission, scheduling, cancellation and delivery are not established by the existing host review or current native protocol. This is a verification gap, not an absent notification feature or a requirement to rebuild the notification system.

Production entry points are `game/mobile/lib/notification_service.dart`: `NativeNotificationGateway.initialize` at269 (no permission prompt), `permission` at290, `requestPermission` at313, `cancelReminders` at335 (only IDs77101–77103), `schedule` at342 (`zonedSchedule`, inexact Android, quiet/no sound/no vibration), `timeZone`/`openSettings` at380/383, and `NotificationService.native` at412. Exact line numbers may shift; the named symbols and source hash in `inspected-file-pins.json` are authoritative. `notification_settings.dart` exposes enable/category/quiet-hour/settings controls. `ReminderLifecycle` waits for successful durable save and rejects stale generation/replay before scheduling. The actual app lifecycle and `Bootstrap` use the production service.

The independent host review has 30 tests and384 departure conditions, including DST, delayed save, return during scheduling, opt-out races, partial failure and recovery. It explicitly says SDK method calls are mocked and native permission/delivery are unqualified. The current-runtime harness replaces reminders at `current_runtime_test.dart:1026–1050` with an adapter that reports unsupported and throws if scheduling is attempted. `platform_smoke_test.dart` tests native audio, ownership clock, worker, rendering and share sheets; it has no reminder scenario. Thus the new 58-cell matrix cannot implicitly close this requirement.

A later bounded probe can use the real production `NotificationService.native` and `NativeNotificationGateway` in a disposable test app/data directory on the permitted iOS simulator and Android emulator. Keep source/candidate/harness hashes, OS and app identity, before/after permission state, scheduler records and visible OS result. Use a seeded reachable timer close to readiness so the production planner creates a near-future reminder; clearly label synthetic time/state. No real two/eight-hour wait or broad matrix repeat is needed to qualify the adapter mechanics.

Checks that would discriminate actual behavior:

- Fresh install/initialization does not request permission or schedule reminders. Only the actual enable control invokes OS permission UI. Exercise refusal and a later explicit retry/settings grant; guest economy and the free route continue.
- With granted permission, depart through the actual lifecycle after a successful save. Inspect pending OS requests for the owned IDs, text, due time, timezone and quiet settings; confirm a short scheduled item appears while backgrounded. Return/disable cancels pending owned reminders without cancelling an unrelated sentinel notification.
- Seed a due time inside quiet hours and a combined Focus/Survey readiness. Observe the production scheduled date shifted outside quiet hours and bounded/bundled IDs, not merely a fake gateway's arguments. A far-future quiet-hours request need not be awaited; inspect its actual OS pending record.
- Revoke permission through OS settings while backgrounded, then return/reopen settings. Observe the denied state, no unintended permission prompt and no gameplay mutation. Re-enable explicitly and confirm scheduling can recover.
- Record any simulator limitation or OS deferral honestly. Android inexact scheduling can be delayed; a timeout is inconclusive/failing delivery evidence, not an excuse to mark delivered. iOS simulator notification support must be observed, not assumed. Physical idle/battery/suspension and accessibility qualification remain external where unsupported locally.

Do not substitute `NoNativeReminderAdapter`, mocked method channels, `FakeNotificationGateway`, simulated callbacks or manually injected Flutter lifecycle notifications for OS permission/delivery observations. OS permission grants made only through an ADB command can prepare a schedule test, but cannot prove the user permission prompt; distinguish those subcases. No production constants, permission breadth, background busy loop or exact-alarm privilege is needed to make this probe concrete.
