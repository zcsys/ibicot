## Bounded operator steps

1. Verify exact serial, AVD name and API35 before a sequence. Bind the new evidence directory, fresh run ID, native action marker and observed app PID. For permission dialogs require actual activity provenance launchedFromPackage=dev.tideglass.game and matching installed app identity; retain raw dumps. Do not interact with other devices or packages.
2. Before each tap, obtain a fresh hierarchy and PNG, inspect the actual image and match exactly one intended enabled/clickable node by package, text/content description, resource ID and bounds. Compute an interior center from the current bounds, never from an earlier attempt or resized display image. No match, duplicate, changed foreground, uncertain identity or stale observation means no tap; refresh and inspect. Do not use a generic automatic permission watcher.
3. Send one explicit UI input event through existing SDK (`adb -s emulator-5556 shell input touchscreen tap X Y`) or the documented Home/Back key event as appropriate. Record UTC, exact argv, selected node attributes/current bounds, coordinates, pre-image/hierarchy hashes and exit status. Immediately capture and inspect post-image/hierarchy/activity state. An exit0 is only command completion; actual native assertions decide qualification. Any second action requires a fresh observation. No blind retry loop.
4. Denial uses the visible Don't allow control only after the fresh bound denial marker. Quiet-cancel uses the visible Allow control if Android presents it. If previously denied state no longer prompts, actual Settings UI may enable only this app's notifications as a separate recorded precondition; never call a permission API or claim a fresh prompt. Navigate by observed Settings/App info/Notifications controls and bind the app-details intent to package:dev.tideglass.game. Record the switch's actual before/after state.
5. Delivery: after the exact background marker, send an actual Home key event, observe launcher/Home and preserve actual app lifecycle. Wait for the emitted due timestamp in real time, without changing any clock. Return only by the observed current Tideglass launcher icon after due, using hierarchy/image plus current package identity; never use notification tap, am start or forced activity launch. App drawer navigation if needed uses freshly observed UI gestures/controls. Native delivered-record and cancellation assertions remain decisive.
6. Revocation: the harness opens real app Settings. Inspect exact app identity, tap observed Notifications and its current allowed switch to OFF, capture before/after; use actual Home then observed app icon to return. If the explicit second denial request prompts, select its visible Don't allow control after its marker. No `pm grant/revoke`, appops set, settings put, service/permission API, fabricated gateway result, data clear, reset or arbitrary force-stop is an operator substitute.
7. Hash all operator files with the run before verification seals where possible. Files produced after native finalization get a separate append-only receipt; never rewrite sealed verification. Keep actual screenshots, selected-node receipts and native outcomes distinct from user reports. Retain both old timeouts as failed/unqualified attempts.

## Primary support and limits

Android documents UI Automator interactions across user and system apps and visible permission-dialog actions: https://developer.android.com/training/testing/other-components/ui-automator . Its legacy API also documents visible element interaction, Settings and Home: https://developer.android.com/training/testing/other-components/ui-automator-legacy . AOSP InputShellCommand sends input events and implements tap using real ACTION_DOWN/ACTION_UP: https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/input/InputShellCommand.java . AOSP dump code obtains the active accessibility hierarchy: https://android.googlesource.com/platform/frameworks/uiautomator/+/dec12c69b4e09679f691050d8fdcab0a5e474258/cmds/uiautomator/src/com/android/commands/uiautomator/DumpCommand.java . Installed-device help is the exact capability observation; these sources explain the distinction from direct permission mutation.

This establishes feasibility of installed observation tools, not successful taps or native reminder qualification. Actual future UI and OS results remain to be observed. No physical device, human usability, store ingestion or notification-banner visibility claim follows from automation. UiAutomator may time out or expose incomplete nodes; preserve failure and do not manufacture a target. S02 network toggles are outside this reminder procedure's first execution; reuse only after its separate approved protocol and actual UI identity are checked.
