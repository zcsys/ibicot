# Android revocation: staged restart-aware qualification

The actual Settings OFF action killed PID 7256 at 19:08:13.889 local with exit reason 8 `PERMISSION CHANGE` and description `PermissionHelper`. The before/after raw screens visibly show Tideglass's notification toggle moving ON→OFF. The old driver lost its VM service; it produced no final result or pre-kill durable checkpoint. That failure stays failed. A later read-only export of its files is not retroactive pre-kill proof and is not an eligible predecessor.

Only four test/tool files are staged. Nothing was promoted, and no production files, Flutter process or device were changed during this assignment. Preparation uses a fresh isolated synthetic directory. It retains the actual fresh-default-off check, explicit OS opt-in, production lifecycle save and at-least-five-minute plan. Before opening Settings, it flushes a checkpoint containing native run/PID identity, the save payload/cursor/snapshot and actual preference/save-slot hashes. The host exports and rehashes those bytes while the exact PID is still alive, then tells the operator the checkpoint is captured. Only an actual Settings revocation and fresh matching permission-change OS exit can yield an interrupted preparation. No preparation is a passed test.

Recovery requires the same candidate/harness/runner/device/label/run ID, exact archived checkpoint, raw files and independently inspectable UI packet. It rejects an old same-process failure, a changed file, wrong PID, other kill reason, stale exit, changed tool source or mismatched action. A new native PID reopens the same fixture, observes actual denial before initialization, then invokes production initialization. It records pending/active IDs before and after so an already empty OS queue is not falsely attributed to production. Both afterward must be empty. It loads the exact durable snapshot, invokes the production permission-gated scheduling path without advancing or rewriting that save, then performs explicit denied re-opt-in and verifies enabled=false persisted. All saved generations and the predecessor checkpoint remain byte-identical.

A remembered enabled=true preference is deliberately preserved on startup while OS permission is denied. That is current production behavior, distinct from effective scheduling or a fresh user's default-off setting. No artificial preference clearing or automatic permission request was added. The final explicit denied re-opt-in persists false using the production service.

The existing real delivery scenario and its 720-second combined observation / 15-minute outer test are untouched. Preparation uses the original revoked path's 180-second Settings observation bound; permission operations retain 150 seconds. Source/artifact identities, selected-emulator refusal rules, scoped cancellation and strict final framework success for recovery remain required. The parent is coordinating a separate semantics-handle diagnosis; this stage does not dispose or manipulate semantics handles.

Validation: 21 new focused Python tests and all 22 existing reminder verifier tests pass, 43 total. Python compilation passes. `host-tests-sealed.log` is the exact latest run; earlier successful host runs remain. The actual saved-payload JSON digest from the preserved delivery report also agrees with the checkpoint verifier's encoding. No Dart formatter/analyzer or native execution was run because that lane is owned by the native agent. **Scoped Dart analysis and a fresh native pair are still required before qualification.** Root must independently review the staged source/patch and any common-harness semantics addendum before promotion.

The actual Android exit reason is consistent with [ApplicationExitInfo.REASON_PERMISSION_CHANGE](https://developer.android.com/reference/android/app/ApplicationExitInfo#REASON_PERMISSION_CHANGE). That API fact is not used to waive matching raw PID/time/UI evidence. This stage does not qualify physical devices, broad notification behavior, M3-05/S26 completion or a finished release.
